# Phase 3 — pre-implementation integration matrix

This matrix is the phase-specific decision record required by the repository rules. It distinguishes runtime integration implemented in Phase 3 from intentionally deferred frontend presentation and Phase 5 gateway authorization.

| Boundary | Ownership / decision before implementation | Phase 3 implementation | Acceptance evidence / status |
|---|---|---|---|
| PostgreSQL / migrations | `catalog_pricing` owns plans, price versions, catalog audit and catalog Outbox. `entitlements_quotas` owns capabilities, assignments, usage ledger, audit and entitlement Outbox. No cross-schema writes. | Separate owner migrations, transactional application services, RLS, immutable price/capability definitions, append-only ledger and immutable idempotency result snapshots. | Isolated PostgreSQL database and restricted non-BYPASSRLS role in `database.rs`; immutability, rollback, concurrency, versioning and tenant isolation tests. |
| Frontend → REST/OpenAPI → BFF | Tenant and platform apps may only call their own REST BFF; neither accesses PostgreSQL, Redis, NATS or internal gRPC directly. | Existing catalog/entitlement REST handlers are exposed by the platform BFF. Phase 3 does not introduce new product screens or client-side cache mutations; those belong to Phase 7. | HTTP/BFF/gRPC acceptance verifies API boundaries. Existing Playwright suites verify both apps' baseline. Phase-specific UI/TanStack Query behavior is N/A because no Phase 3 UI surface is introduced. |
| BFF → owner module by gRPC | BFF owns REST mapping only. Catalog and entitlement business rules remain in their respective Rust modules behind versioned protobuf services. | CatalogPricing and EntitlementsQuotas gRPC services are registered and used by the BFF. Tenant session/CSRF and operator permissions are checked through identity_access; API-key consumption requires `usage.consume`. | `http_grpc_acceptance.rs` and `identity_access_acceptance.rs`: real HTTP-to-gRPC path and authorization. |
| Platform → gateway gRPC | Platform is the authority for quota and entitlement decisions. Gateway calls the shared versioned contract; it does not read platform storage. Signed grants, mTLS identity, replay protection and fail-closed authorization are Phase 5. | `platform-contracts` exposes the versioned API and `bacekend-pasarela::entitlements::GatewayEntitlementsClient` provides typed consume/read calls. No platform database or credential is duplicated in the gateway. | The Phase 3 HTTP acceptance connects the actual gateway client to the running platform gRPC service, consumes quota with an API key and verifies idempotent replay. mTLS identity, signed grants and fail-closed gateway policy enforcement are explicitly deferred to Phase 5. |
| Redis | PostgreSQL remains authoritative for quota counters and idempotency. Redis is not used to decide entitlements or store usage. Redis outage cannot change quota accounting; it delays realtime notification while JetStream redelivery/retry remains available. |
| NATS JetStream / Outbox | Each domain transaction writes its own Outbox record. JetStream delivery is at-least-once; consumers deduplicate by immutable `event_id`. | Realtime / WebSocket / cursor recovery | Realtime journal owns durable scoped cursors. Platform events use `platform_operator`; tenant events must carry a valid tenant ID. WebSocket authorization is performed by the realtime gateway; REST/gRPC cursor replay repairs missed wake signals. | Catalog Outbox's `platform` audience is translated to `platform_operator`; tenant assignment/consumption events remain tenant scoped. Realtime consumer extracts the event traceparent, persists the journal record and signals Redis. | Phase 3 acceptance checks catalog platform cursor and tenant quota cursor using real PostgreSQL and Redis. Existing realtime gateway authorization and multi-replica recovery suites remain required. A dedicated browser screen for Phase 3 events is deferred with Phase 7. |
| Errors / tracing / redaction | Correlation ID is bounded and validated. W3C trace context crosses HTTP/gRPC and asynchronous Outbox/JetStream boundaries. Error envelopes expose stable safe codes, never secrets or SQL payloads. | Outbox writes persist the active traceparent; relay includes it in the envelope; realtime consumer extracts it as the parent span. Audit rows store trace ID and safe details. | Format/Clippy/tests and existing observability/redaction acceptance run in CI. The final run must be green on the exact final SHA. |
| Deployment / migration operation | Apply owner migrations in order; deploy compatible binaries; verify health and rollback plan before closure. | Migration is included in the SQLx owner migrator; no production deployment is performed by this PR. | Deployment and target-environment health evidence must be recorded before claiming production readiness. |

## Explicit non-applicability and deferred boundaries

- **Quota accounting in Redis:** N/A by design. PostgreSQL ledger and transactional advisory locks are authoritative; Redis is only realtime fan-out.
- **New frontend screens in Phase 3:** N/A by phase sequencing. Phase 3 adds backend contracts and BFF endpoints; Phase 7 owns product UI, TanStack Query presentation and screen-specific browser acceptance. No frontend cache is mutated by this phase.
- **Gateway mTLS and live authorization:** deferred to Phase 5. Phase 3 provides the shared gRPC contract and typed gateway client but does not claim signed-grant enforcement or production gateway integration.
- **Production deployment:** not performed by the code PR. It remains a closure gate and must be evidenced separately.

Any change to these decisions requires a reviewed update to this matrix before implementation.
