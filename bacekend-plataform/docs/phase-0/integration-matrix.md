# Matrices de integración — Backend de plataforma

## Alcance de la fase

Fase 0 audita, formaliza decisiones, límites, amenazas y workspace. No crea estado de negocio persistido, mutaciones visibles, usuarios, tenants, pagos, credenciales, contratos RPC ejecutables ni eventos de dominio. La matriz no declara integraciones runtime inexistentes como aprobadas.

## Decisión de alcance de Fase 0

Fase 0 es documental y está cerrada conforme a la decisión explícita del proyecto. Sus comprobaciones son auditoría, ADRs, bounded contexts, threat model, matriz y verificaciones estáticas del workspace. No implementa ni ejecuta runtime; por eso HTTP/BFF/gRPC, Redis, PostgreSQL, JetStream y realtime no son aceptaciones de esta fase.

## Matriz de integración — Fase 1: Fundaciones y observabilidad

Esta matriz se incorpora antes de la implementación. Fase 1 entrega únicamente la infraestructura técnica de BFF, gRPC, salud y telemetría; no introduce operaciones de negocio ni mutaciones persistidas.

La composición física de esta entrega respeta la frontera del monolito modular: `src/main.rs` es el composition root; `apps/bff` es el adaptador REST; `modules/platform_runtime` contiene dominio, caso de uso y adaptador gRPC; `crates/platform_contracts` posee el `.proto` versionado compartido; `platform` contiene configuración y observabilidad transversal. El BFF depende solo del crate de contratos, nunca de la implementación del módulo. Los dominios de tenant, auth, catálogo, billing, pagos y realtime siguen asignados a fases posteriores y no se crean como crates vacíos. El endpoint de salud es operacional y no constituye una función tenant/admin, por lo que no requiere una pantalla React. La prueba acepta el HTTP público de BFF mediante cliente HTTP real y atraviesa un servidor/cliente Tonic real hasta el módulo.

El binario `bacekend-plataform` es un despliegue separado en su VM/VPS. El workspace y lockfile raíz solo se comparten durante build; `bacekend-plataform/deploy/Dockerfile` produce una imagen que ejecuta solo el backend de plataforma. `bacekend-pasarela` y ambos frontends conservan artefactos, entornos, secretos, redes y operaciones independientes. El RPC de `platform_runtime` permanece en loopback dentro del proceso/host de plataforma en esta fase; no es un endpoint de comunicación entre los dos backends.

## Plan de aceptación posterior

Las tres filas de adapters propios son alcance futuro, no evidencia de integración ya implementada. Wompi usa ambientes y llaves distintos para sandbox y producción; Factus requiere validar OAuth y expiración de token; Resend documenta claves de idempotencia para envío. Cada contrato concreto se confirma contra documentación oficial al iniciar su subfase.

| Área | Aceptación mínima de la primera fase ejecutable | Dependencias reales |
|---|---|---|
| Workspace | `cargo metadata`, `cargo check --workspace`, `cargo fmt --all -- --check`; bins separados; sin workspaces anidados. | toolchain Rust. |
| Health/readiness | HTTP real del BFF → RPC real por tonic → API de módulo; propagation W3C/correlation; errores tipados hasta envelope. | runtime del BFF y módulo. |
| PostgreSQL | migraciones del módulo dueño, aislamiento y rollback; detalles SQLSTATE/constraint seguros. | PostgreSQL desarrollo aislado. |
| Redis | solo si la subfase integra estado efímero; TTL, caída, reconexión/backoff, Pub/Sub resubscribe. | Redis desarrollo declarado. |
| JetStream/Outbox | solo cuando el evento durable corresponda al dominio; persistencia, ack/redelivery, deduplicación, reconnect. | PostgreSQL y NATS desarrollo declarados. |
| Observabilidad | logs JSON, eventos de frontera, OpenTelemetry/Sentry configurados externamente, fallo de exportador degradable, redacción. | collector/Sentry de test aislados según integración. |
| Aceptación cross-backend | caller y certificado válidos/rotados y negativos; autorización grant; límite/deadline/replay/recovery/idempotencia. | ambas aplicaciones y configuración mTLS de desarrollo. |
